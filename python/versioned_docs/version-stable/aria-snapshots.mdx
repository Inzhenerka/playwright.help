## Обзор {#overview}

С помощью тестирования снимков в Playwright вы можете проверять дерево доступности страницы по сравнению с заранее определенным шаблоном снимка.

<Tabs
  groupId="python-flavor"
  defaultValue="sync"
  values={[
    {label: 'Sync', value: 'sync'},
    {label: 'Async', value: 'async'}
  ]
}>

```py
page.goto('https://playwright.dev/')
expect(page).to_match_aria_snapshot("""
  - banner:
    - heading /Playwright enables reliable end-to-end/ [level=1]
    - link "Get started":

    - link "Star microsoft/playwright on GitHub":
      - /url: https://github.com/microsoft/playwright

""")
```

## Тестирование утверждений и тестирование снимков {#assertion-testing-vs-snapshot-testing}

Тестирование снимков и тестирование утверждений служат разным целям в автоматизации тестирования:

### Тестирование утверждений {#assertion-testing}

Тестирование утверждений — это целенаправленный подход, при котором вы утверждаете конкретные значения или условия для элементов или компонентов. Например, с Playwright, [expect(locator).to_have_text()](/api/class-locatorassertions.mdx#locator-assertions-to-have-text) проверяет, что элемент содержит ожидаемый текст, а [expect(locator).to_have_value()](/api/class-locatorassertions.mdx#locator-assertions-to-have-value) подтверждает, что поле ввода имеет ожидаемое значение. Тесты утверждений специфичны и обычно проверяют текущее состояние элемента или свойства по сравнению с ожидаемым, заранее определенным состоянием. Они хорошо работают для предсказуемых, однозначных проверок, но ограничены в охвате при тестировании более широкой структуры или вариаций.

**Преимущества**
- **Ясность**: Намерение теста явно и легко понять.
- **Специфичность**: Тесты сосредоточены на конкретных аспектах функциональности, что делает их более устойчивыми к несвязанным изменениям.
- **Отладка**: Ошибки предоставляют целенаправленную обратную связь, указывая непосредственно на проблемный аспект.

**Недостатки**
- **Многословность для сложных выводов**: Написание утверждений для сложных структур данных или больших выводов может быть громоздким и подверженным ошибкам.
- **Затраты на обслуживание**: По мере развития кода ручное обновление утверждений может быть трудоемким.

### Тестирование снимков {#snapshot-testing}

Тестирование снимков захватывает "снимок" или представление всего состояния элемента, компонента или данных в данный момент, который затем сохраняется для будущих сравнений. При повторном запуске тестов текущее состояние сравнивается со снимком, и если есть различия, тест не проходит. Этот подход особенно полезен для сложных или динамических структур, где ручное утверждение каждой детали было бы слишком трудоемким. Тестирование снимков более широкое и целостное, чем тестирование утверждений, позволяя отслеживать более сложные изменения с течением времени.

**Преимущества**
- **Упрощает сложные выводы**: Например, тестирование визуального компонента пользовательского интерфейса может быть утомительным с традиционными утверждениями. Снимки захватывают весь вывод для легкого сравнения.
- **Быстрая обратная связь**: Разработчики могут легко заметить непреднамеренные изменения в выводе.
- **Поощряет согласованность**: Помогает поддерживать согласованный вывод по мере развития кода.

**Недостатки**
- **Чрезмерная зависимость**: Может возникнуть соблазн принять изменения в снимках, не полностью понимая их, что потенциально скрывает ошибки.
- **Гранулярность**: Большие снимки могут быть трудными для интерпретации, когда возникают различия, особенно если незначительные изменения затрагивают большие части вывода.
- **Пригодность**: Не подходит для высоко динамичного контента, где выводы часто или непредсказуемо меняются.

### Когда использовать {#when-to-use}
- **Тестирование снимков** идеально для:
  - Тестирования пользовательского интерфейса целых страниц и компонентов.
  - Широких структурных проверок для сложных компонентов пользовательского интерфейса.
  - Регрессионного тестирования для выводов, которые редко меняют структуру.
- **Тестирование утверждений** идеально для:
  - Проверки основной логики.
  - Тестирования вычисленных значений.
  - Тонко настроенных тестов, требующих точных условий.

Комбинируя тестирование снимков для широких, структурных проверок и тестирование утверждений для конкретной функциональности, вы можете достичь хорошо сбалансированной стратегии тестирования.

## Aria снимки {#aria-snapshots}

В Playwright ARIA-снимки представляют дерево доступности страницы в формате YAML. Эти снимки можно сохранять и впоследствии сравнивать, чтобы проверять, остаётся ли структура страницы неизменной или соответствует заданным ожиданиям. Шаблон задаёт ограничения и не обязательно является полной сериализацией дерева доступности.

Формат YAML описывает иерархическую структуру доступных элементов на странице, детализируя **роли**, **атрибуты**, **значения** и **текстовое содержимое**. Структура следует синтаксису, похожему на дерево, где каждый узел представляет доступный элемент, а отступы указывают на вложенные элементы.

Каждый доступный элемент в дереве представлен как узел YAML:

```yaml
- role "name" [attribute=value]
```

- **role**: Указывает ARIA- или HTML-роль элемента (например, `heading`, `list`, `listitem`, `button`).
- **"name"**: Доступное имя элемента. Строки в кавычках обозначают точные значения, а `/patterns/` используются для регулярных выражений.
- **[attribute=value]**: Атрибуты и значения в квадратных скобках представляют определённые ARIA-атрибуты, такие как `checked`, `disabled`, `expanded`, `invalid`, `level`, `pressed` или `selected`. Атрибуты могут задавать ограничение на конкретное значение, например `[pressed=mixed]`.

Эти значения берутся из атрибутов ARIA или вычисляются на основе HTML-семантики. Чтобы посмотреть структуру дерева доступности страницы, используйте [вкладку Accessibility в Chrome DevTools](https://developer.chrome.com/docs/devtools/accessibility/reference#tab).

## Сопоставление снимков {#snapshot-matching}

Метод проверки [expect(page).to_match_aria_snapshot()](/api/class-pageassertions.mdx#page-assertions-to-match-aria-snapshot) в Playwright сравнивает структуру страницы, представленную в дереве доступности, с заранее заданным шаблоном ARIA-снимка, помогая проверить соответствие состояния страницы требованиям тестирования. Вы также можете использовать [expect(locator).to_match_aria_snapshot()](/api/class-locatorassertions.mdx#locator-assertions-to-match-aria-snapshot), чтобы проверить соответствие определённой части страницы шаблону.

Для следующего DOM:

```html
<h1>title</h1>
```

Вы можете сопоставить его, используя следующий шаблон снимка:

<Tabs
  groupId="python-flavor"
  defaultValue="sync"
  values={[
    {label: 'Sync', value: 'sync'},
    {label: 'Async', value: 'async'}
  ]
}>
<TabItem value="sync">

```py
expect(page).to_match_aria_snapshot("""
  - heading "title"
""")
```

</TabItem>
<TabItem value="async">

```py
await expect(page).to_match_aria_snapshot("""
  - heading "title"
""")
```

</TabItem>
</Tabs>

При сопоставлении шаблон снимка сравнивается с текущим деревом доступности страницы:
* Если структура дерева соответствует шаблону, тест проходит; в противном случае он завершается с ошибкой, указывающей на несоответствие между ожидаемым и фактическим состояниями доступности.
* Сравнение учитывает регистр и нормализует пробельные символы в именах и текстовых значениях. Отступы YAML определяют вложенность.
* Сравнение учитывает порядок: порядок элементов в шаблоне снимка должен совпадать с порядком в дереве доступности страницы.
* Шаблон из одного узла может соответствовать узлу на любой глубине в пределах выбранной страницы или локатора. Несколько узлов верхнего уровня должны соответствовать узлам с одним и тем же родителем и располагаться в том же порядке.

### Частичное сопоставление {#partial-matching}

Вы можете выполнять частичные сопоставления узлов, опуская атрибуты или доступные имена, что позволяет проверять конкретные части дерева доступности без необходимости точных совпадений. Эта гибкость полезна для динамических или несущественных атрибутов.

```html
<button>Submit</button>
```

```yaml title="ARIA-снимок"
- button
```

В этом примере роль кнопки сопоставляется, но доступное имя ("Submit") не указано, что позволяет тесту пройти независимо от метки кнопки.

<hr/>

Для элементов с ARIA атрибутами, такими как `checked` или `disabled`, опуская эти атрибуты, вы можете сосредоточиться только на роли и иерархии.

```html
<input type="checkbox" checked>
```

```yaml title="снимок ARIA (частичное совпадение)"
- checkbox
```

В этом частичном сопоставлении атрибут `checked` игнорируется, поэтому тест пройдет независимо от состояния флажка.

<hr/>

Аналогично, вы можете частично сопоставлять дочерние элементы в списках или группах, опуская конкретные элементы списка или вложенные элементы.

```html
<ul>
  <li>Feature A</li>
  <li>Feature B</li>
  <li>Feature C</li>
</ul>
```

```yaml title="снимок ARIA (частичное совпадение)"
- list:
  - listitem: Feature B
```

Частичные сопоставления позволяют создавать гибкие тесты снимков, которые проверяют основную структуру страницы без навязывания конкретного содержимого или атрибутов.

### Строгое сопоставление {#strict-matching}

По умолчанию будет сопоставляться шаблон, содержащий подмножество дочерних элементов:

```html
<ul>
  <li>Feature A</li>
  <li>Feature B</li>
  <li>Feature C</li>
</ul>
```

```yaml title="Снимок ARIA (частичное совпадение)"
- list:
  - listitem: Feature B
```

Свойство `/children` управляет сопоставлением дочерних элементов узла, в котором оно указано:
- `contain` (по умолчанию): совпадение, если все указанные дочерние элементы присутствуют в заданном порядке.
- `equal`: совпадение, если непосредственные дочерние элементы точно соответствуют указанному списку и порядку.
- `deep-equal`: совпадение, если дочерние элементы и их вложенные дочерние элементы точно соответствуют указанному списку и порядку.

Если ожидаемые дочерние элементы не указаны, `contain` допускает любые дочерние элементы, а `equal` и `deep-equal` требуют их отсутствия. Добавьте `/children: contain` во вложенный узел, чтобы переопределить унаследованное сопоставление `deep-equal` и разрешить в нём дополнительные дочерние элементы.

```html
<ul>
  <li>Feature A</li>
  <li>Feature B</li>
  <li>Feature C</li>
</ul>
```

Следующий снимок не пройдёт проверку, поскольку функция C отсутствует в шаблоне:

```yaml title="aria snapshot"
- list:
  - /children: equal
  - listitem: Feature A
  - listitem: Feature B
```

#### Глобальная настройка режима `children`

Вместо добавления свойства `/children` в каждый снимок можно задать режим сопоставления дочерних элементов по умолчанию для всех вызовов `toMatchAriaSnapshot` в файле конфигурации:

Отдельные снимки по-прежнему могут переопределять глобальную настройку с помощью явно указанного свойства `/children` в шаблоне.

### Сопоставление с помощью регулярных выражений

Регулярные выражения позволяют гибко сопоставлять элементы с динамическим или переменным текстом. Доступные имена и текст могут поддерживать шаблоны регулярных выражений.

```html
<h1>Issues 12</h1>
```

```yaml title="ARIA-снимок"
- heading /Issues \d+/
```

## Генерация снимков {#generating-snapshots}

Создание aria снимков в Playwright помогает обеспечить и поддерживать структуру вашего приложения. Вы можете генерировать снимки различными способами в зависимости от вашей настройки тестирования и рабочего процесса.

### Генерация снимков с помощью генератора кода Playwright {#generating-snapshots-with-the-playwright-code-generator}

Если вы используете [Генератор кода](./codegen.mdx) Playwright, генерация aria снимков упрощается с его интерактивным интерфейсом:
- **Действие "Assert snapshot"**: В генераторе кода вы можете использовать действие "Assert snapshot", чтобы автоматически создать утверждение снимка для выбранных элементов. Это быстрый способ захватить aria снимок как часть вашего записанного тестового потока.
- **Вкладка "Aria snapshot"**: Вкладка "Aria snapshot" в интерфейсе генератора кода визуально представляет aria снимок для выбранного локатора, позволяя вам исследовать, проверять и проверять роли элементов, атрибуты и доступные имена для помощи в создании и проверке снимков.

### Использование [page.aria_snapshot()](/api/class-page.mdx#page-aria-snapshot) и [locator.aria_snapshot()](/api/class-locator.mdx#locator-aria-snapshot)

Методы [page.aria_snapshot()](/api/class-page.mdx#page-aria-snapshot) и [locator.aria_snapshot()](/api/class-locator.mdx#locator-aria-snapshot) позволяют программно создавать YAML-представление элементов дерева доступности в области действия локатора, что особенно полезно для динамического создания снимков во время выполнения тестов.

**Пример**:

<Tabs
  groupId="python-flavor"
  defaultValue="sync"
  values={[
    {label: 'Sync', value: 'sync'},
    {label: 'Async', value: 'async'}
  ]
}>
<TabItem value="sync">

```py
snapshot = page.aria_snapshot()
print(snapshot)
```

</TabItem>
<TabItem value="async">

```py
snapshot = await page.aria_snapshot()
print(snapshot)
```

</TabItem>
</Tabs>

Эта команда выводит aria снимок в области указанного локатора в формате YAML, который вы можете проверить или сохранить по мере необходимости.

## Примеры дерева доступности {#accessibility-tree-examples}

### Заголовки с атрибутами уровня {#headings-with-level-attributes}

Заголовки могут включать атрибут `level`, указывающий их уровень заголовка.

```html
<h1>Title</h1>
<h2>Subtitle</h2>
```

```yaml title="ARIA-снимок"
- heading "Title" [level=1]
- heading "Subtitle" [level=2]
```

### Текстовые узлы {#text-nodes}

Отдельные или описательные текстовые элементы появляются как текстовые узлы.

```html
<div>Sample accessible name</div>
```

```yaml title="ARIA-снимок"
- text: Sample accessible name
```

### Встроенный многострочный текст {#inline-multiline-text}

Многострочный текст, такой как абзацы, нормализуется в aria снимке.

```html
<p>Line 1<br>Line 2</p>
```

```yaml title="ARIA-снимок"
- paragraph: Line 1 Line 2
```

### Ссылки {#links}

Ссылки отображают свой текст или составное содержимое из псевдоэлементов. Адрес назначения ссылки можно сопоставить с помощью свойства `/url`.

```html
<a href="#more-info">Read more about Accessibility</a>
```

```yaml title="ARIA-снимок"
- link "Read more about Accessibility":
    - /url: "#more-info"
```

Значение `/url` также может быть регулярным выражением:

```html
<a href="https://www.youtube.com/channel/UC46Zj8pDH5tDosqm1gd7WTg">YouTube channel</a>
```

```yaml title="aria snapshot"
- link:
  - /url: /https://www.youtube.com/channel/.*/
```

### Текстовые поля {#text-boxes}

Элементы ввода типа `text` показывают содержимое своего атрибута `value`.

```html
<input type="text" value="Enter your name">
```

```yaml title="снимок ARIA"
- textbox: Enter your name
```

### Списки с элементами {#lists-with-items}

Упорядоченные и неупорядоченные списки включают свои элементы списка.

```html
<ul aria-label="Main Features">
  <li>Feature 1</li>
  <li>Feature 2</li>
</ul>
```

```yaml title="снимок ARIA"
- list "Main Features":
  - listitem: Feature 1
  - listitem: Feature 2
```

### Группированные элементы {#grouped-elements}

Группы захватывают вложенные элементы, такие как элементы `<details>` с содержимым summary.

```html
<details>
  <summary>Summary</summary>
  <p>Detail content here</p>
</details>
```

```yaml title="ARIA-снимок"
- group: Summary
```

### Атрибуты и состояния {#attributes-and-states}

Часто используемые атрибуты ARIA, такие как `checked`, `disabled`, `expanded`, `invalid`, `level`, `pressed` и `selected`, представляют состояния элементов управления.

#### Флажок с атрибутом `checked` {#checkbox-with-checked-attribute}

```html
<input type="checkbox" checked>
```

```yaml title="снимок ARIA"
- checkbox [checked]
```

#### Кнопка с атрибутом `pressed` {#button-with-pressed-attribute}

```html
<button aria-pressed="true">Toggle</button>
```

```yaml title="ARIA-снимок"
- button "Toggle" [pressed=true]
```

#### Поле ввода с атрибутом `aria-invalid` {#input-with-aria-invalid-attribute}

Значение `aria-invalid` отображается напрямую. Значение `true` отображается как `[invalid]`, а `grammar` и `spelling` отображаются как `[invalid=grammar]` и `[invalid=spelling]`. Значение `false` опускается.

```html
<input type="text" aria-label="Email" aria-invalid="true" value="not-an-email">
```

```yaml title="aria snapshot"
- textbox "Email" [invalid]: not-an-email
```

```html
<input type="text" aria-label="Bio" aria-invalid="spelling">
```

```yaml title="aria snapshot"
- textbox "Bio" [invalid=spelling]
```
