## Введение {#introduction}

:::warning

Сервис-воркеры поддерживаются в браузерах на базе Chromium.
:::

:::note
Если вам нужно перехватывать запросы, настраивать маршрутизацию или подменять ответы, начните с [Network Guide](./network.mdx). В Playwright есть встроенные API для этих задач. Ниже описано, как работать с запросами, которые отправляют сами сервис-воркеры.
:::

[Service Workers](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API) позволяют браузеру обрабатывать запросы страницы, отправленные через [Fetch API (`fetch`)](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API), а также запросы на загрузку скриптов, стилей и изображений.

Сервис-воркер может выступать **сетевым прокси** между страницей и сетью, чтобы кэшировать ответы или обеспечить работу приложения без подключения. Для этого он регистрирует обработчик [FetchEvent](https://developer.mozilla.org/en-US/docs/Web/API/FetchEvent#examples).

Многие сайты используют сервис-воркеры для незаметной оптимизации. Пользователь может заметить, что сайт работает быстрее, но само приложение ведёт себя одинаково с включённым и выключенным сервис-воркером.

## Как отключить сервис-воркеры {#how-to-disable-service-workers}

В тестах сервис-воркеры можно отключить, чтобы повысить предсказуемость и скорость. Если рабочая версия страницы использует сервис-воркер, её поведение может отличаться.

Чтобы отключить сервис-воркеры, установите параметр контекста `service_workers` в `"block"`.

```python title="conftest.py"
import pytest

@pytest.fixture(scope="session")
def browser_context_args(browser_context_args):
    return {
        **browser_context_args,
        "service_workers": "block"
    }
```

## Доступ к сервис-воркерам и ожидание активации {#accessing-service-workers-and-waiting-for-activation}

Свойство [browser_context.service_workers](/api/class-browsercontext.mdx#browser-context-service-workers) возвращает список сервис-воркеров [Worker]. Если ожидается, что страница запустит [registration](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register) воркера, можно дождаться его появления:

Событие [browser_context.on("serviceworker")](/api/class-browsercontext.mdx#browser-context-event-service-worker) происходит **до** того, как сервис-воркер начинает управлять страницей. Дождитесь его активации, прежде чем выполнять код через [worker.evaluate()](/api/class-worker.mdx#worker-evaluate).

Есть способы дождаться активации, учитывающие конкретную реализацию. Следующий пример работает независимо от неё:

```py
page.evaluate("""async () => {
  const registration = await window.navigator.serviceWorker.getRegistration();
  if (registration.active?.state === 'activated')
    return;
  await new Promise(resolve => {
    window.navigator.serviceWorker.addEventListener('controllerchange', resolve);
  });
}""")
```

}""")

## Сетевые события и маршрутизация {#network-events-and-routing}

Каждый сетевой запрос **сервис-воркера** отражается в объекте [BrowserContext]:
* Срабатывают соответствующие события [browser_context.on("request")](/api/class-browsercontext.mdx#browser-context-event-request), [browser_context.on("requestfinished")](/api/class-browsercontext.mdx#browser-context-event-request-finished), [browser_context.on("response")](/api/class-browsercontext.mdx#browser-context-event-response) и [browser_context.on("requestfailed")](/api/class-browsercontext.mdx#browser-context-event-request-failed).
* Запрос доступен для перехвата через [browser_context.route()](/api/class-browsercontext.mdx#browser-context-route).
* Свойство [request.service_worker](/api/class-request.mdx#request-service-worker) содержит экземпляр сервис-воркера [Worker], а обращение к [request.frame](/api/class-request.mdx#request-frame) **выбрасывает исключение**.

Для сетевого запроса **страницы** свойство [response.from_service_worker](/api/class-response.mdx#response-from-service-worker) возвращает `true`, если запрос обработал обработчик `fetch` сервис-воркера.

Рассмотрим простой сервис-воркер, который выполняет каждый запрос страницы:

Если `index.html` зарегистрирует этот сервис-воркер, а затем запросит `data.json`, появятся следующие события запроса и ответа, а также события сетевого цикла:

| Event                             | Owner            | URL                            | Routed | [response.from_service_worker](/api/class-response.mdx#response-from-service-worker) |
| -                                 | -                | -                              | -      | -                                      |
| [browser_context.on("request")](/api/class-browsercontext.mdx#browser-context-event-request) | [Frame]          | index.html                     | Yes    |                                        |
| [page.on("request")](/api/class-page.mdx#page-event-request)           | [Frame]          | index.html                     | Yes    |                                        |
| [browser_context.on("request")](/api/class-browsercontext.mdx#browser-context-event-request) | Service [Worker] | transparent-service-worker.js  | Yes    |                                        |
| [browser_context.on("request")](/api/class-browsercontext.mdx#browser-context-event-request) | Service [Worker] | data.json                      | Yes    |                                        |
| [browser_context.on("request")](/api/class-browsercontext.mdx#browser-context-event-request) | [Frame]          | data.json                      |        | Yes                                    |
| [page.on("request")](/api/class-page.mdx#page-event-request)           | [Frame]          | data.json                      |        | Yes                                    |

Поскольку сервис-воркер из примера работает как прозрачный прокси:
* Для `data.json` приходят два события [browser_context.on("request")](/api/class-browsercontext.mdx#browser-context-event-request). Один запрос принадлежит фрейму [Frame], другой — сервис-воркеру [Worker].
* Через [browser_context.route()](/api/class-browsercontext.mdx#browser-context-route) можно перехватить только запрос сервис-воркера [Worker]. Запрос фрейма [Frame] за `data.json` перехватить нельзя, поскольку зарегистрированный обработчик `fetch` сервис-воркера обработает его до выхода в сеть.

:::caution

Обращение к [request.frame](/api/class-request.mdx#request-frame) или [response.frame](/api/class-response.mdx#response-frame) выбросит исключение, если у соответствующего [Request] или [Response] свойство [request.service_worker](/api/class-request.mdx#request-service-worker) имеет значение, отличное от `null`.
:::

## Маршрутизация только запросов сервис-воркеров {#routing-service-worker-requests-only}

<Tabs
  groupId="python-flavor"
  defaultValue="sync"
  values={[
    {label: 'Sync', value: 'sync'},
    {label: 'Async', value: 'async'}
  ]
}>
<TabItem value="sync">

```py
def handle_route(route: Route):
  if route.request.service_worker:
    # NB: accessing route.request.frame here would THROW
    route.fulfill(content_type="text/plain", status=200, body="from sw")
  else:
    route.continue_()

context.route("**", handle_route)
```

</TabItem>
<TabItem value="async">

```py
async def handle_route(route: Route):
  if route.request.service_worker:
    # NB: accessing route.request.frame here would THROW
    await route.fulfill(content_type="text/plain", status=200, body="from sw")
  else:
    await route.continue_()

await context.route("**", handle_route)
```

</TabItem>
</Tabs>
